# Claude Code セキュリティ設定監査

ローカルの Claude Code 設定を、バージョン管理されたセキュリティ要件
ファイルと突合し、対応状況と改善方法をレポートする。

## 役割分担

- `scripts/collect_config.py` / `scripts/collect_config.ps1`: 設定の事実を
  読み取り専用で収集する。判定はしない。両者は同じ JSON を返す
- `references/paths.json`: OS 依存の設定ファイルの場所。上流でパスが
  変わったらこのファイルだけを直す
- Claude（このスキルの実行者）: 収集結果と要件を突合し、判定と
  改善方法を書く

判定基準は必ず要件ファイルに置く。このスキル自身は基準を持たない。
基準の改訂は要件ファイルの差し替えで行い、スキルは変更しない。

## 入力

このスキルはコマンドでのみ起動する。引数は 2 つとも省略できる。

```text
/security-audit [project_dir] [requirements_path]
```

| 引数 | 値 | 省略時 |
| --- | --- | --- |
| 監査対象プロジェクト | `$project_dir` | カレントディレクトリー |
| セキュリティ要件ファイル | `$requirements_path` | 同梱の `references/requirements.md` |

置換後の値が空文字なら省略されたものとして扱う。引数の不足を
ユーザーに聞き返さず、省略時の既定で進める。

## 手順

### 1. 前提の確認

設定ファイルからは読めない前提が 1 つだけある。判定を始める前に確認する。

| 問い | 選択肢 | 影響する要件 |
| --- | --- | --- |
| auto mode は意図して使っているか | 意図的 / 意図していない | REQ-004 |

**利用形態は聞かない。** 契約の種別は収集結果の `account` から判定する
（`organizationType` / `seatTier` / `workspaceRole`）。自己申告に頼らない。

そのうえで、個人契約であることを要件の免除に使ってよいのは、**統制対象が
自分以外の利用者である要件**に限る。エージェント自身による設定変更への
防御や、許可の影響範囲の限定は、利用者が 1 人でも成立するため免除しない。

満たさない要件を「個人だから対象外」として消さない。NG として出し、
実施しない判断はユーザーが下す。

### 2. 要件ファイルの検証

要件ファイルを読み、以下を確認する。

- フロントマターに `baseline_version` があること。無い場合は監査を中断し、
  要件ファイルの再生成を求める。基準のバージョンを特定できないレポートは
  監査として成立しないため
- 各要件が見出しに `REQ-NNN` を持ち、`category` / `check` / `target` の
  3 項目を備えていること
- `check` の値が `config` または `manual` であること
- `status: deprecated` の要件は判定対象から外すこと

不備があれば列挙してユーザーに確認する。勝手に補完しない。

### 3. 設定の収集

カレントディレクトリーを移動せず、このスキルのベースディレクトリー
（冒頭に示されるパス）にあるスクリプトを絶対パスで実行する。

収集スクリプトは 2 実装ある。**同じ JSON を返すので、環境に応じて使い分ける。**

Windows 環境では、Python の有無を確認せず、最初から PowerShell 版を使う。

```powershell
# Windows の場合は常にこちら
& "<スキルのベースディレクトリー>/scripts/collect_config.ps1" "<監査対象の絶対パス>"
```

Windows 以外では Python 版を使う。

```bash
# Windows 以外の場合
python3 "<スキルのベースディレクトリー>/scripts/collect_config.py" "<監査対象の絶対パス>"
```

どちらを使ったかはレポートの「収集状況」に書く。

監査対象のパスは必ず引数で渡す。`$project_dir` が空のときは、省略せずに
カレントディレクトリーの絶対パスを渡す。スクリプトの引数省略時の既定は
実行時のカレントディレクトリーであり、スキルのディレクトリーへ移動して
から省略すると、監査対象がスキル自身になってしまうため。

出力 JSON をそのまま判定材料にする。スクリプトが読めなかったファイル
（`exists: false` や `parse_ok: false`）は、それ自体をレポート冒頭の
「収集状況」に記載する。

### 4. 突合と判定

判定するのは `check: config` の要件だけで、3 値を使う。

- **OK**: 収集した設定が target の条件を満たす
- **NG**: 条件を満たさない
- **非該当**: target にプラットフォーム条件が明記されていて、収集結果の
  `platform` がその条件に当たる（Windows 限定の要件を macOS で監査する
  場合など）。前提を根拠に非該当とするのは auto mode の 1 件のみで、
  それ以外に広げない

target に明記が無い要件を、実行時の判断で非該当にしてはならない。
「この機能はこの OS では動かないはず」と気づいた場合も同じで、判定は NG や
非該当にせず、「要件外の所見」に要件の書き方の問題として書く。判定基準を
要件ファイルの外に置くと、同じ設定でも実行のたびに判定が変わるため。
条件の追加は要件ファイルの差し替えで行い、このスキルは変更しない。

非該当は「リスクが無い」ではなく「その設定では統制できない」を意味する。
統制を成立させる別の手段（別のプラットフォームで動かす、隔離環境を使う）が
あるなら、レポートの理由欄にそれを書く。

`check: manual` の要件は**判定しない**。人が定期的に確認する性質のもので、
毎回「要手動確認」として並べても読まれないため、レポート末尾の
「定期確認事項」に参考として列挙するだけにする。

設定だけでは判定しきれない `check: config` の要件が出てきた場合は、
その場でユーザーに聞かず、NG とせず、**要件の書き方の問題**として
レポート末尾の「要件外の所見」に記載する。

判定の原則:

- 設定のスコープ優先順位は managed > local > project > user。同一キーが
  複数スコープにある場合、有効な値がどれかを明示して判定する。
  permissions の deny はどのスコープにあっても有効
- 「設定が存在しない」と「設定が要件を満たさない」を区別する。前者は
  デフォルト挙動が要件を満たすかで判定する
- 推測で OK にしない。根拠となる設定キーと値を判定欄に必ず書く

### 5. レポート生成

Markdown ファイルで出力する（markdown スキルの規約に従い
markdownlint-cli2 でエラーゼロにする）。構成は次のとおり。

```markdown
# Claude Code セキュリティ監査レポート

- 基準バージョン: <baseline_version をそのまま転記>
- 監査日: <collect_config.py の collected_at から>
- 対象: <project_dir>
- Claude Code バージョン: <collect_config.py の出力から>

## 収集状況

<読めなかった設定ファイルがあれば記載。全て読めたなら
「全ファイル収集済み」の一行>

## サマリ

| 判定 | 件数 |
| --- | --- |
| OK | n |
| NG | n |
| 非該当 | n |

## 判定詳細

<要件 ID 順。NG を先頭グループに、次に非該当、最後に OK>

### REQ-NNN: <要件名> — NG

- 現状: <該当する設定キーと実際の値。無ければ「設定なし
  （デフォルト挙動: ...）」>
- 要件: <target の内容>
- 改善方法: <具体的な設定変更。settings.json への追記内容を
  コードブロックで示す。どのスコープに書くべきかも明記>

### REQ-NNN: <要件名> — 非該当

- 理由: <手順 1 で確認した前提、または収集結果の platform と、それが
  当たる target の条件>
- 代替: <その統制を成立させる別の手段。無ければ「なし」>

## 定期確認事項（参考）

<check: manual の要件を列挙する。判定はしない>

- REQ-NNN <要件名>: <何を確認するとよいか 1 行>
```

改善方法の書き方:

- コピーして使える JSON 断片を示す。「deny に追加してください」だけで
  終わらせない
- 書き込み先スコープを推奨付きで示す。組織で強制すべきものは managed、
  チーム共有は project、個人は user
- Enterprise 管理機能（managed settings の配布など）が使えない環境向けの
  代替運用があれば 1 行添える

### 6. レポートの自己チェック

出力前に次を確認する。数が合わないレポートは判定を疑われる。

- サマリの件数の合計が、判定詳細の見出し数と一致すること
- 判定詳細の見出し数が、`check: config` の要件数と一致すること
- `check: manual` の全要件が「定期確認事項」に列挙されていること
- `status: deprecated` の要件がどこにも出ていないこと

一致しない場合は、数え直してから出力する。

## 受容したリスクの扱い

NG の要件について、ユーザーが「実施しない」と判断した場合は、判定を OK に
書き換えず、NG のまま残したうえでレポート末尾の「受容したリスク」に理由を
記録する。監査の価値は対応済みの件数ではなく、どこにリスクが残っているかを
言えることにある。

ユーザーの明示的な判断が無いまま、この節に項目を足してはならない。

## してはいけないこと

- 設定ファイルの書き換え。このスキルは監査のみを行う。修正はレポートを
  見たユーザーが行う
- 要件ファイルに無い独自基準での判定。気づいた問題が要件外なら
  レポート末尾に「要件外の所見」として分離して書く
- `baseline_version` の無いレポートの出力
